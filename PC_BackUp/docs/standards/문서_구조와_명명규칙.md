# 문서 구조와 명명 규칙

AI로 만든 산출물을 어디에 어떤 이름으로 둘지 정한 **1차 가이드라인**입니다.

> **이 문서는 각 프로젝트 저장소로 복사해서 씁니다.** Claude는 지금 작업 중인
> 저장소 밖의 파일을 읽지 못하므로, 여기(표준 저장소)를 참조만 걸어두면 동작하지
> 않습니다. `docs/standards/문서_구조와_명명규칙.md` 로 복사해 넣으세요.
> 절차: [템플릿 사용법 4단계](../templates/README_템플릿_사용법.md).
> 이 원본이 갱신되면 각 프로젝트의 복사본도 분기마다 한 번씩 최신화하세요.

> **이 구조는 제안입니다.** 프로젝트 성격에 따라 조정하세요.
> 다만 **팀 안에서는 같은 구조를 쓰는 것**이 중요합니다. 사람마다 다르면
> 나중에 아무도 찾지 못합니다.

---

## 1. 폴더 구조

프로젝트 저장소의 `docs/` 아래에 둡니다.

```
docs/
├── review/       분석·리뷰 결과        (AI 산출물, 계속 쌓임)
├── design/       설계·구조 문서        (오래 유지, 계속 참조)
├── flow/         동작 흐름·시퀀스      (오래 유지)
├── manual/       사용자·조작 매뉴얼    (외부 공유용)
├── reference/    참고 자료·조사        (외부 스펙, 장비 사양)
├── push/         푸시 요약             (변경 이력)
└── issue/        이슈 관련 상세 자료   (선택)
```

### 각 폴더의 판단 기준

| 폴더 | 넣는 것 | 판단 질문 |
| --- | --- | --- |
| `review/` | 분석 결과, 문제 조사, 감사 | "이번에 조사한 결과인가?" |
| `design/` | 아키텍처, 모듈 경계, 설계 결정 | "6개월 뒤에도 볼 것인가?" |
| `flow/` | 시퀀스, 상태 전이, 이송 경로 | "동작 순서를 설명하는가?" |
| `manual/` | 조작법, 화면 설명 | "장비 사용자가 볼 것인가?" |
| `reference/` | 통신 스펙, 장비 사양, 외부 문서 정리 | "우리가 만든 게 아닌가?" |
| `push/` | 푸시 단위 변경 요약 | "무엇을 왜 바꿨는지 기록인가?" |

**`review/` 와 `design/` 구분이 헷갈릴 때**:
일회성 조사면 `review/`, 계속 참조할 기준이면 `design/`.
`review/` 에 있던 내용이 계속 쓰이게 되면 `design/` 으로 승격시키세요.

## 2. 파일명 규칙

### 기본 형식

```
YYYY-MM-DD_#이슈번호_영문슬러그_KO.md
```

예:

```
2026-08-06_#42_Loadlock_Timeout_Analysis_KO.md
2026-08-06_#45_Gate_Display_Sync_KO.md
```

### 규칙 설명

| 요소 | 이유 |
| --- | --- |
| `YYYY-MM-DD` | 정렬하면 시간순. 언제 파악한 내용인지가 중요합니다 |
| `#이슈번호` | **이슈 ↔ 문서 양방향 추적.** 가장 중요한 부분 |
| 영문 슬러그 | 한글 파일명은 일부 도구에서 깨집니다 |
| `_KO` | 한국어 본문 표시 (영문 문서와 섞일 때 구분) |

### 이슈 번호가 없는 경우

이슈 없이 작업했으면 생략합니다. 다만 **가능하면 이슈를 먼저 만드세요.**

```
2026-08-06_Interlock_Audit_KO.md
```

### 오래 유지되는 문서는 날짜를 빼세요

`design/`, `flow/`, `manual/` 은 계속 갱신되므로 날짜가 방해됩니다.

```
docs/design/Architecture_Overview_KO.md
docs/flow/Wafer_Transfer_Sequence_KO.md
docs/manual/Operator_Manual_KO.md
```

**갱신 이력은 git이 기록합니다.** 파일명에 날짜를 넣지 마세요.

## 3. 문서 안에 반드시 넣을 것

### 분석·리뷰 문서 (`review/`)

```markdown
# <제목>

- 이슈: #42
- 작성: 2026-08-06 / 홍길동
- 대상: `LoadlockManager.cs`, `InterlockManager.cs`
- 관점: 타임아웃 처리

## 결론
(3줄 이내. 바쁜 사람은 이것만 읽습니다)

## 확인한 것
(파일 경로와 라인. 근거)

## 발견한 문제
(위험도 순)

## 확인하지 못한 것
(중요. 다음 사람이 여기서 이어받습니다)

## 다음 단계 제안
```

**"확인하지 못한 것"을 반드시 쓰세요.**
이게 없으면 다음 사람이 어디까지 검증됐는지 알 수 없어서 처음부터 다시 합니다.

### 설계 문서 (`design/`, `flow/`)

```markdown
# <제목>

- 최종 갱신: 2026-08-06
- 적용 범위: <어느 모듈/화면>

## (본문)

## 미해결 / 논의 필요
```

## 4. AI에게 시키는 방법

폴더와 이름을 매번 타이핑하지 말고 AI에게 맡기세요.

```text
지금까지 분석한 내용을 문서로 정리해줘.

위치와 파일명은 팀 규칙을 따라줘:
- 위치: docs/review/
- 이름: 오늘날짜_#42_영문슬러그_KO.md

포함할 내용:
- 결론 3줄
- 확인한 파일 (경로와 라인)
- 발견한 문제 (위험도순)
- 확인하지 못한 것
- 다음 단계 제안

작성 후 그 파일만 커밋 승인. 메시지에 (#42) 포함.
```

프로젝트의 `CLAUDE.md` 에 이 규칙을 적어두면 매번 설명하지 않아도 됩니다.

```markdown
## 문서 작성 규칙
분석 결과는 `docs/review/YYYY-MM-DD_#이슈번호_영문슬러그_KO.md` 로 저장한다.
"확인하지 못한 것" 섹션을 반드시 포함한다.
```

## 5. 처음 만들 때

프로젝트에 이 구조가 없으면 AI에게 시키세요.

```text
docs/ 아래에 문서 폴더 구조를 만들어줘.
review, design, flow, manual, reference, push 폴더와
각 폴더에 어떤 문서를 넣는지 설명한 README.md 를 만들어줘.

빈 폴더는 git이 추적하지 않으니 README.md 를 각각 넣어줘.
```

## 6. 최소한 이것만

부담스러우면 이 셋만 지키세요.

1. **분석 결과는 `docs/review/` 에** — 흩어지지 않게
2. **파일명에 이슈 번호** — 나중에 찾을 수 있게
3. **"확인하지 못한 것" 섹션** — 다음 사람이 이어받을 수 있게
