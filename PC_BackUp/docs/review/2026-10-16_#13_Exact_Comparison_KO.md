# 복원 전 비교의 정확한 파일 일치 판정

- 이슈: #13 — https://github.com/SuhunKim/Program_Backup/issues/13
- 작성: 2026-10-16 / Codex
- 대상: `PC_BackUp/Services/BackupComparisonService.cs`
- 관점: 복원 전 비교 정확성

## 결론

복원 전 비교에서 모든 공백을 제거해 동일함으로 취급하던 보조 비교를 제거했다.
이제 파일 내용이 한 바이트라도 다르면 내용 변경으로 표시하며 복원 확인 단계로 진행한다.
같은 바이트의 파일은 기존과 동일하게 변경 없음으로 판단한다.

## 확인한 것

- `BackupComparisonService.Compare`는 파일 크기와 스트림 바이트 비교 결과를 사용한다.
- 기존 `TextFilesEqualIgnoringWhitespace`는 JSON 문자열 내부 공백도 제거해 실제 값 변경을 숨길 수 있었다.
- `RecoveryControl.BuildCompareConfirmMessageAsync`는 변경 목록이 비어 있으면 복원을 진행하지 않으므로 정확한 비교가 필요하다.

## 변경 사항

- 공백 무시 비교의 fallback과 사용되지 않는 관련 helper를 제거했다.
- 파일 확장자와 관계없이 실제 파일 바이트로 일치 여부를 판단한다.
- 공백·줄바꿈·인코딩만 다른 경우도 내용 변경으로 표시된다. 이는 정확한 복원 판단을 위한 의도된 동작이다.
- 새 서식 무시 옵션은 도입하지 않았다. 필요하면 표시 전용 기능으로 별도 설계한다.

## 사용자 검증 절차

실제 운영 데이터 대신 별도 시험용 프로그램 폴더와 백업을 사용한다. 복원 전 비교 옵션을 켠다.

1. 같은 경로의 JSON을 현재 `{"label":"AB"}`, 백업 `{"label":"A B"}`로 구성한다. 내용 변경으로 표시되어 복원 확인 단계로 진입해야 한다.
2. XML 텍스트 값의 내부 공백, INI 값의 공백도 각각 변경으로 탐지해야 한다.
3. CRLF/LF, 들여쓰기, UTF-8 BOM 차이는 실제 바이트 차이이므로 내용 변경으로 표시되어야 한다.
4. 같은 크기에서 한 바이트만 다른 바이너리와 크기가 다른 파일 모두 변경으로 표시되어야 한다.
5. 바이트가 완전히 같은 파일만 있으면 기존처럼 변경 없음으로 표시해야 한다.
6. 현재에만 있는 파일·백업에만 있는 파일의 상태와 취소 처리도 유지되는지 확인한다.

## 확인하지 못한 것

- 저장소 지침에 따라 빌드·프로그램 실행·실데이터 복원은 수행하지 않았다. 사용자 수행 예정이다.
- 실제 운영 XML의 서식 차이 빈도와 새 변경 표시량은 측정하지 않았다.
- 다른 이슈의 XML 부분 적용·롤백·공통 작업 잠금은 이 변경 범위에 포함되지 않는다.
